# T13 — classes and membership

Implemented 26 September 2026. In live mode, signed-in approved teachers can create a class and rotate its code. Signed-in learners preview the class title and teacher alias, then confirm membership. The code is a 96-bit random value shown only in the create/rotate response; PostgreSQL stores only its SHA-256 hash. Rotation invalidates the old code without removing current members. Reusing a code is idempotent; a removed membership can rejoin only with a valid current code.

The service role is confined to server modules. Each SQL function rechecks teacher/learner role and class ownership; RPC execution is denied to authenticated and anonymous clients. The join function locks the matching class, counts attempts per verified learner account and globally in 15-minute windows, and returns no roster. Invalid and rotated codes have the same response. The global 1,000-attempt bound is a pilot ceiling. No client-supplied actor ID is accepted. Existing class and membership RLS keeps reads scoped.

`POST /api/classes` accepts title/grade band; `POST /api/classes/:id/code` rotates; `POST /api/classes/preview` and `/api/classes/join` accept a code. All require same-origin JSON, bounded to 1 kB, and return `no-store`. `/classes` provides the teacher and learner forms. Joining has an explicit confirmation. The class list is RLS-scoped. The UI does not show a code later because it cannot be recovered from the stored hash.

Local verification: `npm run test:classes` executes all migrations in PGlite and checks role restrictions, ownership, invalid/rotated codes, preview without membership, reuse, rotation, and attempt limits. Existing PGlite database/preparation/session checks, targeted lint, typecheck and production build pass. These are SQL stubs, not hosted Supabase Auth/JWT checks. Hosted synthetic-account verification remains pending configured non-local access. No Docker, paid call, real pupil data, commit, push or deployment was used.
