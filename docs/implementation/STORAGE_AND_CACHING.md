# Document storage and caching

Updated 1 October 2026 after the requested remaining-feature implementation and synthetic hosted Storage checks. Actual observations and remaining Clerk/browser acceptance are distinguished below.

## Where an attachment goes

1. `POST /api/chat/attachment` checks the origin and current learner identity, bounds the multipart body, and accepts PDF/DOCX files up to 4 MiB. Server-only worker parsers enforce 50 pages/sections, 30,000 extracted characters and a 15-second deadline.
2. After validated extraction, a service-only SQL reservation checks the active account and its **20-document cap** under a profile lock. Original bytes upload to the existing **private Supabase Storage** `source-documents` bucket at an owner/document UUID path. `uploaded_documents` in **Supabase Postgres** retains the safe display name, byte count, complete bounded extraction and upload state. Only a successful Storage write plus ready metadata returns a usable document ID. A failure after an acknowledged upload attempts cleanup; failed cleanup retains its durable record. An ambiguous upload response retains `uploading` state for operator reconciliation because a remote writer may still finish. The new `20261001000100_documents.sql` migration is required.
3. The preview explicitly offers the complete saved extraction or an editable excerpt. Original upload storage occurs before this choice. Choosing content does not create a preparation or call a model. The current entry draft/history can live in that account's browser-tab `sessionStorage`; this is neither a verified assessment nor global learner memory. New chat clears that account's entry draft/history. The document library provides private reuse, download and original removal.
4. Sending Notes calls `enterChat` → `createPreparation` → the `create_preparation` database function. Supabase **Postgres** stores metadata/hash in `source_documents`, extracted text in `source_chunks`, and preparation data in `preparation_jobs.partial_results`. Generated lesson snapshots and saved session/messages also live in Postgres. Owner checks and RLS protect access; admin-client operations still explicitly enforce ownership.
5. Full-document requests send `document_id` and `source_mode: "full"`. The server reads the owner's saved extraction, preserving actual PDF pages/DOCX sections, parser/hash, coverage and warnings; browser text never supplies page provenance. The existing 30,000-character/50-page bounds apply without 8,000-character truncation. Edited excerpts use `source_mode: "excerpt"` and up to 8,000 characters; they become explicitly pasted/edited text with attribution to the original but **no original page claim**. A topic alone remains scope, never an answer key.

App-user Storage policies remain denied. Owner-authenticated server routes enforce all access using the existing server-only admin client. Downloads are bounded by the recorded size (maximum 4 MiB), use attachment/octet-stream/nosniff headers and `private, no-store`; there are no public or reusable signed URLs. `/api/sessions/:id/sources` exposes the owner's exact saved lesson references and available original download links through the installed Animate UI/Radix dialog. It distinguishes source-matched excerpts from factual verification and original page references from edited notes.

## Implemented cache

`src/lib/ingestion/cache.ts` reuses extraction results for the same authenticated learner and identical file bytes, kind and MIME type. It coalesces simultaneous identical requests and clones each result so one caller cannot alter another caller's coverage/text. Context such as grade is recalculated on every request. Every route request checks identity before reading the body and rechecks it after acquiring upload bytes, before cache admission. Origin and body/file limits are checked before lookup; MIME changes cannot bypass parser validation.

- At most **60 seconds from insertion**, **two entries per learner**, **16 entries per Node process**, oldest insertion evicted first. Existing parser bounds cap each result. Expiry uses both a timer and a checked deadline, so a suspended serverless process cannot serve expired entries after resuming.
- Cache values contain extraction results/promises, not original file bytes or model assessments. Original bytes are needed only while the parser is running. Failed parses are removed immediately and may be retried.
- Account deletion clears this process's entries once durable access revocation begins. Work admitted before revocation may still finish its response; this is not synchronous cancellation. Other instances retain entries until their short expiry, but future requests require current identity; this is not distributed erasure. A restarted/cold instance reparses normally. No Redis, external cache service, shared public cache or new dependency is introduced.
- HTTP responses remain `no-store`. Auth, ownership, mutable sessions, objective evidence and results are not placed in this cross-request cache.

The existing provider already persists exact successful request replays in `usage_ledger`: its request digest includes owner, retry key, AI role, prompt version, model and full body. Repeating the same confirmed request reuses its response without another provider dispatch. This is retry caching, not semantic reuse across different learners or different answers. Unknown provider outcomes remain reserved for reconciliation; caching never triggers an automatic paid retry.

## Retention and deletion

Originals and their extraction metadata remain until the learner removes the original or deletes the account. This explicit retention for reuse supersedes the historical proposed seven-day original-file default; there is no automatic expiry claim. Twenty files at 4 MiB bounds one account's originals to 80 MiB. Removing an original first marks it unavailable, removes its Storage object, then removes its metadata. A Storage failure retains retryable deletion metadata. Existing saved lesson excerpts remain, because immutable evidence needs its source; account deletion removes those private records too.

Account deletion first disables access through the existing durable identity marker. It then clears this process's extraction cache, removes all Storage objects/metadata, and only then deletes the external identity and profile. A concurrent reserved upload is visible as `uploading`, so deletion remains disabled/retryable until the write finishes. New reservations reject the deletion marker. An ordinary cleanup failure becomes `failed`, visible as needing cleanup in the library and removable by the learner or account cleanup. Runtime termination during a Storage operation can leave an `uploading` record; the operator workflow below recovers it. Do not delete metadata first or manipulate `storage.objects` SQL rows to simulate object removal. No automatic stale-upload erasure is claimed.

### Operator recovery for interrupted uploads

The existing `npm run ops:manage` command provides `documents-status` to list up to 100 nonready document IDs, owners, states and timestamps, without document text or filenames. It remains restricted to the confirmed non-local synthetic test project. Inspect the relevant application worker/logs before confirming that no upload writer remains. Wait at least five minutes from reservation; time alone is not proof that a remote write ended.

```powershell
'{"action":"documents-status"}' | npm run ops:manage
# Replace the placeholder UUIDs with the specific row from the status response.
'{"action":"document-reconcile","ownerId":"OWNER_UUID","documentId":"DOCUMENT_UUID","confirmDocumentId":"DOCUMENT_UUID","confirmedNoActiveWriter":true}' | npm run ops:manage -- --confirm
```

Reconciliation requires matching document UUID confirmation, `--confirm` and `confirmedNoActiveWriter: true`. It fences a stale `uploading` row to `failed` before using the normal Storage deletion path, then removes metadata only after object removal succeeds. A late worker cannot mark that row ready. Failed removal retains metadata for retry. Account deletion can then be retried. This is a real operator command with local mock regression coverage, not a claim of a hosted cleanup run.

## Verification and sources

The 1 October follow-up also exercised actual hosted Storage with a synthetic PDF: byte-for-byte private download, foreign-owner and public denial, full/excerpt provenance, and deletion retaining immutable lesson excerpts.
